# v0.7 assessment and implementation plan

Class: experimental software architecture assessment, not a Standard.
Date: 2026-10-16. Prepared before implementation. Status: selected implementation
direction under the user's v0.7 authorization; completion requires verification.

## Baseline and readiness

Published v0.6 is commit `bcbb477479d4f5e5988a7cd078a47bd76eb3ac57`.
Development branch: `codex/gr-os-v0.7`. The unchanged baseline passes 38/38
Release CTest tests (179.96 s on this workstation). Source hashes were checked
against the v0.6 manifest before edits; source archive, installed SDK, Python
facade and benchmark binaries are preserved under ignored `build/baselines/v0.6`.
Checked-in evidence is under `docs/validation/v0.6-pre-v0.7`.

The assessment covers the v0.6 review, verification and performance reports,
Layer 3 Library/Expr/Function, qualified relational implementation, installed
diagonal extension, Layer 4 planning/scheduling/transaction contracts, kernel
historical reconstruction and physical backend interfaces. R8 documents 07,
27, 28, 29, 31 and 32 are design inputs, not binding specifications. Programme
authority and conceptual source authority remain separate. Relevant foundation
passages consulted include FM-007 Part II pp.32-33 and 36-39 (context, incidence,
reidentification and occurrence multiplicity), and FM-005 Chapter 5 pp.14, 29,
168-169 (evidence, auxiliary assumptions and revisability). No theory or
programme publication is changed by this implementation.

| Existing facility | Assessment | v0.7 consequence |
|---|---|---|
| Sealed Library with separately extensible types, representations, operators and providers | Sufficient native extension contract; callbacks are trusted code | Reuse explicit registration before sealing |
| Expr/Function and prepared runtime plans | Adequate reusable computations; expressions share one Library | Demonstrate native composition, not a second language or scheduler |
| Historical selection and qualified incidence | Preserves occurrences, revisions and qualifications | Analyze this representation without reconstructing history independently |
| Session immutable parsed cache | Already shares source internally, but inspect deep-copies JSON | Add a narrow owner-retaining const inspection view |
| Runtime cancellation/resources | Cooperative callbacks, bounded admitted jobs; not process isolation or hard RSS limits | Direct APIs have explicit limits/stop tokens; scheduled operators reuse runtime |
| CMake exports and diagonal extension | Genuine installed native consumer; no stable cross-toolchain C++ ABI | Independently build/install/relocate packages against exact SDK |
| Python Context | Built-in registration only; independent DLL handles cannot safely be shared | Persistent package owners plus explicit compact typed interchange |
| Existing independent-package test | Requires ignored historical v0.5 SDK | Remove mandatory historical state; retain optional actual older-SDK check |

v0.6's speedups depend on immutable validation/index reuse. Recreating a Library
and Runtime, deep-copying all source JSON, or retransmitting full historical
wrappers at each module call would erase part of that benefit. Current Python
base64 payload access already incurs a one-time transport cost. This increment
must measure it separately, not call the Python path zero-copy.

## Selected architecture and alternatives

Layer 2 consists of ordinary independent packages. Analytical, formal-model,
visualization, domain, workflow and connector categories describe purpose; they
are not six new inheritance hierarchies. A package may expose direct typed APIs,
register Layer 3 extensions, or both. Pure computational packages have no
automatic publication authority. Privileged connectors need separately designed
effect, authentication, disclosure and recovery contracts; none are implemented.

Use conventional CMake and Python packaging for dependencies. Small versioned
manifests describe distribution identity, semantic exports, SDK compatibility,
dependencies, effects and trust. Python entry-point enumeration provides
discovery without importing package code. Explicit activation is trusted code
execution. There is no custom dependency solver, central DLL loader, universal
plugin ABI or security sandbox. Manifest validation checks declarations, not
whether native code obeys them.

Considered alternatives: a generic plugin host would centralize lifecycle but
add binary/security promises we cannot yet enforce; Python-only tools would be
simpler but fail the native reusable/high-performance goal; routing every scene
through the runtime adds planning overhead without useful scheduling semantics;
using JSON for every native call loses immutable sharing. The selected design
uses native typed owners and a deliberately copied portable boundary for Python
packages. RPC/process isolation remains the appropriate future option for
untrusted modules, rather than claiming in-process registration is isolation.

## Bounded pilots

1. **gr_relational_analysis**: owner-retaining NetworkView over a validated
   qualified incidence value, exact selected occurrence indexing, role/temporal
   distributions, occurrence and distinct-neighbor degrees, connected components
   including isolated participant-owner vertices, and comparison of qualified
   recording states. Preserve owner versus target roles, repeated/n-ary/higher
   order occurrences and resolved target versions. Unknown participant-bearing
   profiles remain owner records, not automatically ontology Relations.
   Compare only the same workspace and selection rules initially. Record
   continuity is not proof of persistence of a real-world relationship.
2. **gr_visualization**: independently built package consuming the analysis
   snapshot, configurable incidence columns and categorical temporal bands,
   immutable structured Scene and deterministic SVG export. Positions are
   constructed display coordinates; temporal classes are not elapsed time.
   Every glyph maps to exact source identities/occurrences. Filters and omissions
   are explicit. Output is returned to the caller; export writes/publication are
   caller actions. XML escaping, invalid-character handling and output limits are
   tested. No web application or frontend framework.
3. **gr_diagonal conformance demonstration**: retain its specialized type/operator
   extension; update its distribution version deliberately for SDK 0.7. Compose
   an explicitly mapped integer analysis vector with diagonal weighting and
   standard reduction. This illustrates a formal transformation, not an
   empirically validated social model or universal representation of mathematics.

NetworkView retains complete qualified source custody. Its NetworkSnapshot
shares immutable native topology/context. Portable encode/import copies only
that projection, with source-value identity (specification, payload and
computational provenance), revision pins, snapshot digest and declared losses.
The wire does not grant itself source-validated status: imported snapshots are
structurally validated only. Neither snapshot nor SVG proves omitted historical
derivation, truth, evidential sufficiency or institutional acceptance.

C++ consumers can compose registered operators in one Library and use shared
direct views. Python analysis retains a native handle across calls; visualization
imports the compact snapshot through its own facade. Both expose essential
analysis/render capabilities. Arbitrary external native-provider registration
into Python gr_os.Context remains deferred and must not be advertised.

## Implementation sequence and ownership

1. Preserve baseline and write this plan plus ADR-0007 before source edits.
2. Add QualifiedView and analysis native package/tests/benchmarks.
3. Add visualization native package/tests/benchmarks against the agreed snapshot.
4. Add independent C/Python facades, CMake exports, wheels, relocated composition
   consumers and fresh-checkout-compatible packaging tests; update diagonal.
5. Add small metadata/discovery API and Python-native conformance example;
   integrate documentation, review errors/lifetimes/authority and test fixtures.
6. Run appropriate Release and ASan suites including installed consumers, inspect
   rendered output, compare unchanged v0.6 workloads and measure end-to-end new
   workflows. Record failures and corrections, then final source/evidence hashes.
7. Update review, verification, README, AGENTS, changelog and roadmap; stop for
   architectural review. No Layer 1 implementation or legacy migration.

## Acceptance and measured trade-offs

Native tests use hand-computed occurrence/component/degree fixtures, archived
target resolution, contradictory qualifiers, physical versus semantic revision
distinctions, provenance-only identity changes and incompatible selections.
Snapshot tests reject malformed indices, duplicate identities, forged digests
and budgets. Lifetime tests release original sources/sessions while views remain;
facade registries acquire shared owners before work and free memory in their
originating DLL. Cancellation is cooperative and tested at actual scan points.
Visualization checks deterministic mappings, duplicate occurrences, temporal
uncertainty, escaped malicious labels and explicit loss reporting.

Installed tests copy package source outside the core source tree, use installed
headers/libraries only, install and relocate dependencies, build external C++
consumers and isolated Python wheels, and exercise discovery without activation.
Wrong SDK/dependency versions and absent dependencies fail clearly. Fabricated
metadata rejection tests are identified as fixtures; optional actual archived
SDK builds are different evidence. Matching compiler/runtime/configuration is
required; CMake version acceptance is not binary ABI qualification.

Benchmarks separate historical acquisition, first indexing, repeated analysis,
prepared execution, compact snapshot encode/import, scene layout, SVG encoding
and Python import/transport. Retained memory and output bytes accompany timings.
Preserve v0.6 unchanged-workload evidence and report regressions, cache costs,
host variability and untested backends. Dense scenes remain output-size bound;
caps reject rather than silently truncate. GPU, distributed execution, hard
isolation, connector protocols, full causal analysis and general scene engines
are deferred.
