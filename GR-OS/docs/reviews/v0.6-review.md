# v0.6 architectural review

Class: implementation assessment. Maturity: experimental. Date: 2026-10-15 JST.
This review covers the authorized Layer 3 maturation increment and its bounded
independent-package consumer. See the [initial assessment](v0.6-assessment-and-plan.md)
and [ADR-0006](../../decisions/ADR-0006-layer3-maturation.md) for the decision history.
Test and measurement outcomes are recorded separately in [verification](../verification.md).

## Assessment and resulting design

The v0.5 logical-type, representation, generic-operator and physical-provider
boundaries remain useful. They allow a sparse matrix, a qualified history and a
numeric column to share execution infrastructure without sharing an ontology or
storage schema. The largest measured costs arose inside validation and access
paths; replacing the scheduler or introducing a VM would not remove that work.

The implementation therefore keeps Layer 3 as a small typed composition language
and uses Layer 4 for plans/jobs/policy, Layer 5 for historical meaning and Layer 6
for physical storage/execution. It adds the missing reuse and package boundaries:

| Concern | v0.6 choice | Cost or limit |
|---|---|---|
| Immutable validation | Library-local weak payload owner plus exact specification and tag | Equivalent copies miss; bounded metadata; validator must be pure/thread-safe |
| Specialization | Once per immutable expression call node | Fresh binding still makes a pinned concrete catalog/plan; no global plan cache |
| Host iteration | Owning checked rank-one range with endian-safe loads | No device memory, automatic vectorizer, fusion or streaming executor |
| Qualified source processing | Bounded session retaining parsed source, record/version indexes and occurrence inventories | Source bytes still embedded in outputs; new owners fully decoded/checked |
| Composition | Multi-output Function with explicit typed substitution and binding | No textual language, recursive functions, effect system or executable serialization |
| Numerical computation | Checked integers and specified ordered finite machine arithmetic | No implicit promotion, approximate providers or parallel floating reassociation |
| Distribution | Independently installed C++ source package with exact SDK version | Matching toolchain/runtime/configuration; no cross-compiler binary ABI |
| Python extension access | Package-owned synchronous C facade | Copies inputs/results; no shared opaque gr_os-handle registration |

These choices avoid an elaborate dependency solver, dynamic plugin loader, second
scheduler or universal tensor type. The independently built diagonal structure
registers its own type, representation and operator, and composes with standard
reduction through Function and the existing runtime. No kernel switch was added
for it. Its exact-version dependency is deliberately conservative until an API
compatibility policy and additional platforms have evidence.

## Correctness and semantic boundaries

Validation reuse never treats a claimed provenance digest as proof. Values retain
immutable storage owners; exact logical/provenance/carrier checks still run. A weak
certificate cannot keep an allocation budget charged after the caller releases
the value. Library isolation pins validator semantics. Relational sessions retain
decoded state separately with explicit entry/wire-size bounds and weak raw owners;
those charges do not measure JSON allocator overhead or process RSS.

Qualified outputs retain their selected revisions, accounts, participant occurrence
keys, temporal interpretation, source wrappers and declared losses. A computational
count is neither an accepted fact nor an institutional judgment. Cache-on/off byte
equivalence and hostile/new-owner cases protect this distinction. Kernel record
semantics, storage schemas, publication barriers, frozen retries and ACID scope
were not reconstructed in this increment.

The [numerical contract](../numeric-data.md) distinguishes mathematical domain,
physical representation, machine equality, missingness and arithmetic order.
`Determinism::Exact` means the specified machine result under the qualified profile;
it does not promise exact real arithmetic or universal CPU/GPU bit equality. The
initial floating execution gate is genuine MSVC x64 with strict floating controls.
Other builds can store those values and execute checked integers, but floating
execution needs separate conformance qualification. Complex multiplication rounds
each named component intermediate and rejects nonfinite intermediates. Different
algebraic rewrites can therefore have different admissibility.

The new `gr.numeric.sum@1` extends the missing-first policy already used by
`gr.data.sum@1`: determine whether a present result is required before arithmetic.
For a present result, each checked addition follows input order; an overflowing
prefix fails even if later values would bring the mathematical total into range.
The extended numerical domains have a new operation identity. Existing behavior
does not silently change under an old ID.
Scalar/batch provider comparisons validate access-path agreement, while expected
bit and integer oracle fixtures supply independent arithmetic expectations.

Native modules are trusted process code. Registration grants no record authority,
authentication or secure containment. Allocation budgets cover tracked owned
buffers, not all temporary memory. Cancellation is cooperative: validation/inference
callbacks lack stop tokens, and a serialized provider waiter cannot leave until
the active invocation releases the mutex. Hard isolation requires another boundary.

## Performance interpretation

The [measured analysis](../validation/benchmark-v0.6-analysis.md) separates matched
v0.5/v0.6 whole workloads from current-build access and cache experiments. The old
sources, installed SDK and executables were preserved before edits; repeated
alternating-order pairs expose host variation. Counters and opt-in phase timing
measure actual validation/decode/derivation work, but are not a sampled CPU or
hardware-counter profile.

Batch access and removal of repeated immutable work provide substantial gains in
the tested table/sparse pipelines. No blanket speedup follows: small fixed-cost
paths, new-owner validation, source encoding, transport and plan construction still
matter. Worker count is not automatically useful parallelism. The narrow fused host
reference lacks the pipeline's full contracts and is not an interchangeable GR
implementation. Memory charges, logical copy bytes and cumulative process peaks
have different scopes and are reported accordingly.

## Alternatives and deferred work

A content-addressed global certificate store could reuse copies, but needs
validator provenance, custody, collision and eviction contracts. A shared typed
source carrier could avoid JSON embedding but needs a new lifetime/interchange
contract. Neither is justified merely by the existence of a cache hotspot.

Fusion or a JIT may help many tiny numerical nodes once equivalence rules cover
nulls, checked overflow and floating intermediates. Coarse extension-defined
operators already offer a simpler path. Internally parallel kernels can reuse the
provider boundary later; they need thread-budget cooperation and deterministic or
tolerant arithmetic policies. GPU/DLPack integration additionally needs device
ownership and completion/stream synchronization. No such backends are claimed here.

Arrow, SciPy and broader NumPy integration are useful adapters rather than a
replacement for logical typing. The [interoperability review](../interoperability.md)
records copying, validity, duplicate handling and qualification-loss obligations.
No large external numerical dependency was added for an unimplemented claim.

## Readiness for Layer 2

**The architecture is sufficient for selected independent host CPU analysis,
modeling and visualization modules within the implemented contracts.** New custom
mathematical structures and pure exact operators can compose without changing the
semantic kernel or scheduler. A visualization module can consume explicit results
and lineage; it does not need to become a kernel type. Development should start with
one representative module and explicit correctness/performance targets.

This is not general scientific-library or production-platform readiness.
Approximate statistical/causal solvers, large graph/history queries, reusable
runtime parameters, streaming, heterogeneous devices and unrestricted third-party
Python registration need additional contracts. Most can extend the existing
boundaries; the evidence does not guarantee that every future workload will avoid
architectural change. Broad Layer 2 implementation remains paused for user review.

Resolve the [next decisions](../planning/open_questions.md) before expansion:
the first real consumer/workload, numerical reference/acceptance policies,
supported package/toolchain matrix and trust, source custody/scale, and whether
streaming or stronger cancellation is actually required. No application migration
or standards promotion is implied by this software milestone.
