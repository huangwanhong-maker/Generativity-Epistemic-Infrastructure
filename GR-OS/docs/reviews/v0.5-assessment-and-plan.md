# v0.5 architectural assessment and development plan

Class: implementation design and review record. Status: selected bounded implementation direction, 2026-10-14. This is neither an adopted Standard nor a claim of application compatibility.

## Assessment

The current foundation has unusually useful separation already: Layer 5 value and operation descriptors pin exact nominal contracts; record envelopes and history remain a different semantic system. Layer 6S provides physical snapshots/CAS and receipt recovery; Layer 6E provides owned host buffers and prepared execution. Layer 4 seals catalogs, selects implementations, validates complete dataflow graphs, schedules bounded jobs and coordinates explicit publication. Replacing those components to introduce another scheduler, tensor runtime or VM would have substantial cost without a demonstrated benefit.

The v0.4 experimental consumer demonstrates checked int64 buffers and history selection, but is not yet a language: every concrete type/operation is manually registered, data layout carries much of the type information, composition is a physical runtime graph, and parameterized logical descriptions are absent. Runtime graphs deliberately execute every supplied node. A logical expression system earns its place through generic inference, representation-independent identity, root reachability, immutable composition and source/transform descriptions; it does not earn a second execution engine.

Review covered the current public headers, kernel registries and numerical contracts, planner/scheduler/catalog, transaction/history reconstruction, compact history, buffers, SDK registries and installed consumer tests, the experimental data module and benchmarks. R8 documents 26/28/31/32 and related handoff material were compared with actual code. In particular, the existing `core::graph` projection discards qualifications and cannot serve as the qualified historical dataset. `core::temporal` validates explicit downward-closed cuts; a draft's broader automatic-closure proposal is not implemented behavior. The foundation/standards reading informing the relational pilot is recorded in its module documentation.

Before edits, unchanged v0.4 passed 28/28 tests (46.18 s); 161 source/document hashes remained unchanged. `build/baselines/v0.4/` preserves sources, installed binaries, Python facade and benchmark runners. `docs/validation/v0.4-pre-v0.5/` preserves evidence and the preservation manifest. These are a local comparison baseline, not a release or performance assertion about v0.5.

## Selected architecture

1. A structural `Type` contains an exact versioned family, child types and bounded semantic parameters. A registered family validates admissibility and declares inspectable traits. Type parameters can describe shapes, units or other structures without a core enum of mathematical kinds. Dynamic row counts belong in validated values in the initial modules.
2. A separate versioned representation binds a logical type to an existing kernel carrier (JSON, bytes or owned buffers), and validates the mapping. Layout lives in that representation and its buffer descriptors. Persistent encoding is a separate storage/serialization concern. There is no assertion that an in-memory tensor, CSR matrix or incidence view is its logical subject.
3. Generic operators infer output specifications and specialize into exact kernel operation contracts plus one or more physical providers. Family descriptions, children, representations, attributes and contracts participate in deterministic bindings. Callbacks are trusted native code; descriptor fingerprints identify stated contracts, not proof that providers are correct.
4. Immutable lazy expressions retain a sealed library. Explicit sharing lowers one computation once. Compilation selects reachable nodes, pins named input bindings, builds a fresh concrete catalog and delegates to the existing planner. Prepared programs can run asynchronously on the existing runtime. Expression templates can be rebound for bounded chunks; there is no persistent stream scheduler or hidden latest-state read.
5. Source acquisition for historical data is explicit and eager, pinning physical and semantic revisions. Subsequent transformations are pure/exact. Qualifications, archived source records, role occurrences and declared selection/aggregation losses remain distinguishable. Derived counts express recorded participation, not truth, causality or acceptance.

The fresh specialization catalog is deliberate: Layer 4 catalogs are permanently sealed. Mutating a shared runtime catalog after plans exist would weaken its guarantees. Program compilation pays a measurable setup cost; prepared plans are reusable. A global specialization cache, automatic fusion or compiler backend should follow measurements and explicit invalidation/semantic rules.

## Alternatives and trade-offs

| Alternative | Benefit | Reason not selected for v0.5 |
|---|---|---|
| Only extend the Layer 4 graph | Smallest immediate diff | Generic logical identity and representation inference would leak into a concrete execution contract; loses the meaningful lazy/root-selected frontend |
| Full static dependent type system / textual DSL | Strong compile-time shape proofs and syntax | Shapes are often observed at runtime; parser, solver and diagnostics costs precede a demonstrated requirement |
| One tensor/Arrow dataframe universe | Mature optimized kernels/interchange | Would make arbitrary mathematical structures and qualified histories subordinate to a layout/ecosystem |
| Python-only expression engine | Fast prototyping | Would duplicate inference and ownership rules and leave native consumers without the same language |
| New compiler/VM/distributed runtime | Broad optimization potential | Repeats working Layer 4 responsibilities and introduces unmeasured complexity |
| Typed C++/Python frontend lowering to existing plans | Clear distinction with working execution | Selected; runtime validation and specialization cost remain explicit |

Keep exact nominal family versions rather than infer compatibility from semver. Keep traits descriptive until a rewrite rule names its numerical and algebraic preconditions. Int64 arithmetic uses checked operations and ordered reductions. Initial finite f64 storage/interchange, if exposed, does not promise floating-point arithmetic semantics. Approximate and effectful computation remain deferred by the existing execution gate.

## Bounded implementation and validation sequence

- Implement structural types, separate representation registry, generic operators, immutable expressions, named inputs, lowering, deterministic bindings and result lineage.
- Implement nullable columns/tables and checked integer selection/transformation/reduction with shared buffer ownership and explicit null policies.
- Implement qualified history selection, role-indexed incidence and explicitly qualified counts over pinned revisions; test historical edits and omissions.
- Independently register a CSR matrix family/representation and checked matrix-vector operation, with canonical sparse input constraints.
- Expose the same native engine through additive ABI 1 operations and Python handles, reusing plan/job/buffer leases and CLI dispatch. Test actual NumPy copy-in/read-only view-out when available. Document why raw buffers alone do not establish Arrow, SciPy or DLPack compatibility.
- Run targeted conformance, all existing regressions, installed C/C++/Python and CLI consumers, sanitizer checks, and measured pilots. Report preparation separately from execution and transport. Preserve evidence and stop for review.

No application or legacy migration is part of this stage. No speculative GPU, JIT, MPI, general query optimizer, scientific model, universal ontology, automatic publication or production-readiness claim is included.
