# v0.7 architectural review

Class: implementation assessment. Maturity: experimental. Date: 2026-10-17 JST.
This covers the bounded Layer 2 increment selected in the
[assessment and plan](v0.7-assessment-and-plan.md) and
[ADR-0007](../../decisions/ADR-0007-independent-layer2-packages.md).
Acceptance results belong in [verification](../verification.md); the existence of
an API or example is not evidence that every platform or scale is qualified.

## Assessment and resulting boundaries

The existing layered foundation is sufficient for independently developed native
analysis, mathematical and visualization packages. Its registries already separate
logical types, representations, operators and physical implementations. Its runtime
already owns planning, jobs, resources and publication. Layer 2 needs specialized
methods and explicit composition contracts, not another implementation of those
facilities. Repeated core changes are unnecessary for packages that fit the
documented extension points; unfamiliar representations can be registered without
adding mathematical structures to kernel switches.

The new foundation is deliberately small: package metadata/discovery and normal
CMake/Python distribution. A narrow const owning inspection lease exposes already
validated Layer 3 source state; a public Python value descriptor exposes existing
native metadata for correct package import. The remaining new logic belongs in
the independent packages. Layer 5 history and Layer 4 transaction semantics are
unchanged. Analysis and rendering do not automatically publish their results.

| Responsibility | Selected owner | Important limit |
|---|---|---|
| Historical meaning and reconstruction | Existing kernel/transaction coordinator | Analysis does not create another historical validator |
| Computational typing and prepared execution | Existing Library, Expr, Function and runtime | Native operators share one Library; arbitrary Python external registration is absent |
| Qualified network methods | gr_relational_analysis | Exact bipartite recorded-incidence statistics; no causal or real-world identity inference |
| Visual projection and export | gr_visualization | Deterministic scene/SVG, not a physical geometry or frontend application |
| Specialized formal structure | gr_diagonal | Checked integer diagonal operation; no universal tensor/graph requirement |
| Dependency installation | CMake and Python packaging tools | Exact native SDK/source-build contract; no binary ABI promise |
| Discovery | gr_os.modules metadata enumeration | Explicit activation executes trusted code; metadata is not a sandbox |

The two new packages are source packages with independent projects, public headers,
manifests, tests, exports and Python facades. They remain under `packages/` for
development convenience; the installed consumer deliberately does not compile
against central source paths. This distinction matters more than adopting a
polyrepo layout before release ownership is decided.

## Useful methods and composition

The analysis package indexes immutable qualified incidences once and retains source
custody. It provides occurrence degrees, distinct-neighbor degrees, role/temporal
distributions, connected components including isolated owners, and comparisons of
recorded states under matching workspace/selection rules. Relation-owner and
participant-target vertices are separate tagged roles. Repeated, n-ary and
higher-order participation remains explicit. This is a particular analytical
projection with a stated contract, not the GR ontology itself.

The visualization package consumes the typed snapshot through direct functions.
Incidence columns and categorical temporal bands expose exact source mappings,
filters and losses. They preserve indeterminate/unclassified temporal cases rather
than inventing a chronology. SVG uses a bounded fixed subset with escaped text,
generated element IDs and embedded projection metadata. Dense occurrences can
overlap visually, and fonts vary by renderer; structured mappings remain available.

The installed composition example selects actual tracked history, computes an
incidence and registered summary in one prepared computation, and renders a source-
retaining view. Its mathematical contrast explicitly maps target occurrence degrees
to an ordered integer vector, applies independent diagonal weighting, and reduces
through the standard module. The index mapping and constant weighting assumption
are retained. A weighted count is not an empirically validated measure of social
importance or institutional worth.

## Identity, scientific interpretation and authority

Source-value identity binds specification, payload and computational provenance.
Snapshot identity binds the portable projection. Scene identity also binds visual
configuration and the local validation basis. These are distinct identities because
they describe different things. Same source topology with a new physical pin or
different computational provenance need not have the same source-value identity.

Native NetworkView retains the complete qualified source. Its native Snapshot
shares immutable topology/context, can outlive the view, and does not itself
retain the qualified source. Portable snapshots omit source wrappers,
archive/artifact bodies and full histories; imported data receives structural
validation only. A claimed digest cannot prove omitted derivation. The validation
basis is assigned locally, never elevated by a transmitted flag.

Scheduled Layer 3 providers receive carriers rather than complete DataValue
provenance. Their report payload therefore uses carrier-scoped identity; Program
materialization supplies the full computational lineage. Direct reports can bind
the complete source value. Representation validation checks structure/conservation,
not independent factual truth or a replay of absent source records.

Native and Python modules execute with process privileges. Caches, quotas and
callbacks do not enforce tenant isolation, restricted disclosure or institutional
authorization. A package advertising external effects has no permission to perform
them merely because it was discovered or installed. Future connectors require
separate authority and durable outcome protocols. Existing frozen publication
retries and uncertain-outcome contracts remain intact.

## Practical trade-offs and alternatives

Direct C++ composition shares owners and avoids serializing the selected qualified
source at each boundary. Python uses persistent analysis owners and copied compact snapshot
interchange across separately linked package libraries. That is an honest and
testable boundary, but still allocates/serializes/revalidates data. The main SDK's
initial byte export uses base64 JSON internally. Python cannot currently splice
arbitrary external providers into one gr_os.Context; metadata discovery does not
change that limitation.

A universal native plugin ABI would reduce some integration friction but require
stable code-loading, allocation, callback and lifetime contracts across compilers.
A process service boundary would provide stronger isolation but add transport and
deployment costs. A Python-only ecosystem would be easier to begin but would not
exercise independent native high-performance tools. Mandatory runtime tasks for
every scene would add planning overhead without useful scheduling semantics.
The selected design leaves these alternatives available without implementing them
prematurely.

Retained views trade memory for repeat-call efficiency. Portable snapshots and
scene documents are bounded package formats, not streaming containers. Rendering
large scenes is output-size bound and deliberately rejects excessive inputs rather
than silently truncating. Cancellation is cooperative in native loops. The package
Python methods are blocking and do not expose cancellation or custom native Limits
in this increment. Resource limits are logical quotas, not hard process RSS caps.

## Next architectural decisions

The next useful evidence should come from one realistic general or academic
workflow, with explicit dataset sizes, custody rules, uncertainty, latency and
reproducibility needs. Select it before adding more generic infrastructure.
Then decide whether the limiting boundary is Python transport/provider registration,
large-history indexing, scientific numerics, visual scale, or multi-user authority.
Each suggests a different engineering investment.

Additional platform/toolchain qualification, compatible source-version policy,
binary release ownership, untrusted-module isolation, approximate algorithms,
streaming/device execution, interactive clients and connectors remain open.
Application and legacy migration require a separately authorized slice and explicit
GSP/GRRP compatibility decisions. v0.7 ends with architectural review; it does not
start Layer 1 implementation.

## Acceptance and performance implications

Release passed 40/40 tests and the selected ASan suite passed 39/39. Targeted
final corrections separately passed nine installed Python cases and 127 native
visualization checks in both configurations. Exact scope, exclusions and initial
failures are in [verification](../verification.md).

[Measurements](../validation/benchmark-v0.7-analysis.md) retain the large serial
v0.6 improvement on the matched workload, while exposing slower scheduled/transport
cases and substantial host variability. Native snapshot sharing is cheap; source
import/validation, portable parsing and scene/SVG output remain substantial. A
1,024-owner synthetic publication-to-SVG workflow took about 3.45 s in the accepted
local capture, so interactive large-graph performance is not established. Reuse
owners for repeated methods, and choose real workload/latency/custody requirements
before deciding whether to invest in shared Python composition, incremental sources
or more compact scene transport. The increment is complete and stops here for review.
