# v0.5 architectural review

Class: implementation review. Maturity: experimental. Date: 2026-10-15 JST; assessment and implementation began 2026-10-14. Verification and measurements are recorded in the linked evidence reports; this document does not assert standards adoption, scientific validity or application migration compatibility.

## Architectural finding

The foundation is expressive enough to continue broader Layer 3 development through extensions. It now has a coherent logical type and operator language rather than a collection of unrelated utility functions. The three pilots exercise materially different representations and semantics through the same composition and execution interfaces. This is a foundation for future tooling, not yet a complete dataframe engine, numerical platform, stream processor or portable executable language.

The useful layer boundary is now concrete: Layer 3 infers and specializes logical computation; Layer 4 binds and executes a concrete plan; Layer 5 validates record/history and exact operation contracts; Layer 6 supplies storage and physical execution. Mathematical families and representations are extensions. Source acquisition and publication remain explicit boundaries, and domain methods/applications remain outside this stage.

The [initial assessment](v0.5-assessment-and-plan.md) and [ADR-0005](../../decisions/ADR-0005-extensible-computational-language.md) preserve alternatives and the selected plan. The previous foundation was retained because it already supplied the difficult execution, ownership, transaction and recovery contracts. The only semantic addition to Layer 4 is bounded optional plan context, justified by a demonstrated provenance-identity defect; empty context preserves previous plan identity behavior.

## What changed

| Foundation | Implemented result | Deliberate boundary |
|---|---|---|
| Logical types | Versioned family + child types + bounded parameters, native validators and traits | No universal tensor enum, inferred semver compatibility, automatic cast or static dependent-type solver |
| Representation | Separate registered logical-to-carrier mapping, validated layout and ownership | Logical identity is not memory layout or persistence encoding |
| Operators | Native generic inference, concrete contracts, multiple selectable physical providers | Descriptors are not proofs, executable plugins or optimizer licenses |
| Language | Immutable literals, named inputs, multi-output calls, selected roots and explicit sharing | No parser, VM, automatic CSE, fusion or reassociation |
| Execution | Existing prepared plans/jobs, async execution, quotas, cancellation and policy | No second scheduler, GPU, JIT or distributed engine |
| Provenance | Pinned input identities, complete recipe, qualified historical sources and explicit losses | Computational results do not become accepted facts or published records automatically |
| Interfaces | C++ modules plus additive C/Python data, expression and program handles | Python does not independently implement inference or operators |

The common language core is independent of the standard, sparse and relational modules. A library is permanently sealed; expressions and prepared programs retain its callbacks and values. Each program specializes into an owned concrete catalog. Family/representation descriptions are recursively pinned rather than relying only on a type's spelling. Runtime policy still checks exact lowered operation IDs.

## Contrasting pilots

**Nullable tabular computation.** Named heterogeneous columns carry independent logical element/nullability descriptions and physical buffer/validity views. Selection, checked int64 affine transformation, comparison, explicit-null filtering and ordered reduction compose into lazy programs. Optional scalar results preserve missingness rather than overloading zero. Views retain their owners; full-width int64 operands avoid bounded JSON metadata numbers. Finite f64 storage is supported without silently supplying an arithmetic/tolerance policy.

**Qualified relational history.** An eager coordinator read pins actual physical and semantic revisions. A bounded bytes representation retains current wrappers, archived directly pinned referents, recording context and qualifications. Role-indexed incidence preserves n-ary/repeated/parallel/higher-order participation. Temporal interpretation retains selected order accounts, exclusions and unresolved/cyclic/unsupported reports; it does not infer event order from recording order. Role filtering and counts retain exact occurrence keys and their losses. Counts mean recorded participation occurrences, not factual relationships or causation.

**Independent mathematical extension.** A separate sparse module installs the matrix family, CSR representation and checked matrix-vector operator. Two providers implement the same declared result/traversal contract. Missing sparse entries mean exact zero; duplicate or unsorted coordinates fail instead of silently consolidating. Tests compare providers with independent dense expectations and adversarial overflow/shape cases. This path requires no new kernel type switch or runtime scheduler.

## Important engineering findings

The implementation review exposed a real identity gap: physical payload/specification equality alone did not bind external source qualifications into a plan. Materializing one recipe's result under another recipe could otherwise misattribute lineage. An optional `Graph.context` now pins the Layer 3 recipe ID into plan/cache identity without an extra execution barrier. Native and SDK materialization use actual successful job results. This establishes in-process association, not authentication of an arbitrary C++ result structure or external provenance claim.

Recipe size also needs checking before execution. A recipe fitting the metadata limit can exceed it after result-envelope overhead. The compiler now preflights the complete provenance envelope; deeply nested successive derivations remain explicitly bounded. This favors an honest failure over successful computation followed by unrepresentable lineage.

Aggregate output lineage is separately capped by the compilation metadata budget, so high output fan-out cannot multiply a near-limit recipe into gigabytes of serialized metadata. Shared immutable lineage is a worthwhile future optimization. Native helpers validate caller-constructed schemas before indexing; the SDK rejects typed buffers at the raw packed-octet constructor boundary, preserves native interpretation in NumPy conversion, and rolls back all returned handles when Python multi-output wrapping fails.

Physical buffer identity is not universal mathematical equality. A strided view and a dense copy can have the same logical values and different physical hashes. Only explicit expression sharing reuses a node; future common-subexpression or conversion optimizations need operation-specific equivalence rules.

The qualified relational pilot intentionally favors reconstructible correctness: validators recompute derivations from retained source. This creates repeated parsing/validation/source-copy costs. The correct next optimization is likely retained immutable source objects plus exact validation reuse, with clear custody and lifetime rules, rather than weakening validation or dropping qualifications.

## Performance interpretation

Preparation, validation, execution, materialization and language transport have different costs. Fresh catalogs make semantic ownership straightforward but are a visible compilation cost. Prepared programs should be reused when inputs stay fixed; named templates can bind successive finite chunks. The latter is useful bounded processing, not persistent streaming or dynamic runtime parameters.

Operators are coarse native loops over host buffers. The current threaded backend allows independent expression nodes to run concurrently; a single standard/CSR/relational provider is not automatically SIMD-vectorized or internally parallel. Checked prefix arithmetic constrains reassociation and parallel reductions. Any faster provider must preserve the selected exact contract or introduce a separately authorized numerical contract.

The final Release suite passed 35/35 cases; selected AddressSanitizer coverage passed 34/34, with the unchanged legacy Python capacity suite excluded and optional NumPy skipped only in the sanitizer environment. The [verification report](../validation/verification-v0.5.md) gives exact coverage and qualifications.

The [benchmark analysis](../validation/benchmark-v0.5-analysis.md) makes the main performance limitation explicit: a 262,144-row six-node pipeline takes about 1,115 ms prepared serially, while the qualified 256-relation transform takes about 928 ms before materialization. Repeated validation, source copying and generic element access need profiling and measured fast paths before a broad Layer 2 ecosystem. The unchanged runtime comparison is mixed and noisy, with small-dispatch/four-worker regressions to monitor. No GPU/HPC claim follows from this extensible provider boundary.

## Decisions before a broader Layer 2 ecosystem

1. **Numerical contract policy.** Choose floating/complex domains, nonfinite/null behavior, tolerances, reference calculations and reproducibility requirements. Do this before approximate providers or compiler rewrites.
2. **Extension distribution and trust.** Specify executable package identity, dependency/version pinning, validator provenance and supported loading/lifetime model. Exact descriptor hashes do not identify machine code or isolate an extension.
3. **Representative workloads and scale.** Set concrete latency/throughput/data-size targets. Use measurements to prioritize specialization caching, validation reuse, zero-copy source retention or coarse kernels.
4. **Recipe and source packaging.** Decide portable replay, source availability, custody/access/retention and independent validation. Current inspectable recipes are bounded descriptions, not executable archives with all artifacts.
5. **Parameter and streaming model.** Decide whether tools need reusable runtime parameters, bounded chunk iterators or continuous streams with backpressure/recovery. Each has different effects and source-pinning obligations.
6. **Interoperability scope.** Select actual Arrow/SciPy/DLPack/graph adapters and their null, duplicate, layout, device and loss policies. NumPy host ownership evidence cannot stand in for these contracts.
7. **Tooling boundary.** Select a small first Layer 2 tool family whose scientific/methodological meaning is explicit. Do not encode a motivating research model into the kernel merely because it is the first consumer.

The layering approach remains clear and workable. The next increment should deepen measured contracts and extension ergonomics before accumulating a broad operator catalogue. Legacy compatibility/migration still requires a separate deliberate semantic crosswalk and authorization. Stop here for architectural review.
