## Release

```powershell
& "$cmakeBin\cmake.exe" -S . -B build -G 'Visual Studio 17 2022' -A x64 `
  -DGR_BUILD_TESTS=ON -DGR_BUILD_BINDINGS=ON -DGR_BUILD_CLI=ON `
  -DGR_BUILD_EXAMPLES=ON -DGR_BUILD_EXPERIMENTAL_DATA=ON `
  -DGR_BUILD_PYTHON_BUFFER=ON -DGR_BUILD_BENCHMARKS=ON `
  -DGR_REQUIRE_PYTHON_TESTS=ON -DGR_TEST_TIMEOUT_MULTIPLIER=1
& "$cmakeBin\cmake.exe" --build build --config Release --parallel 4
& "$cmakeBin\ctest.exe" --test-dir build -C Release --output-on-failure
```

The complete Release run passed 28/28 CTest cases in 38.93 seconds. A subsequent
SDK-only run after the Python version gate and test-only sanitizer runtime staging
change passed 6/6 cases in 27.87 seconds:

```powershell
& "$cmakeBin\ctest.exe" --test-dir build -C Release --output-on-failure `
  -R '^(python_binding|python_runtime|python_buffers|example_python|example_runtime|installed_sdk)$'
```

`installed_sdk` installs and relocates the exported CMake package, compiles C and
C++ consumers against that prefix, builds and installs a pure Python wheel into
a build-local target, and exercises the optional compiled buffer exporter and
native CLI. The final Release consumer prefix is `build/p/2a41e3b0/relocated`.
The tested wheel is `build/p/2a41e3b0/wheels/gr_os-0.4.0-py3-none-any.whl`.
The final watchdog-only CMake regeneration uses the default multiplier 1; it
does not change the native binary or exported SDK targets.

`ctest-v0.4-sdk-final.txt`, `ctest-v0.4-sdk-final-details.txt`, and

## AddressSanitizer

```powershell
& "$cmakeBin\cmake.exe" -S . -B build-asan -G 'Visual Studio 17 2022' -A x64 `
  -DGR_BUILD_TESTS=ON -DGR_BUILD_BINDINGS=ON -DGR_BUILD_CLI=ON `
  -DGR_BUILD_EXAMPLES=ON -DGR_BUILD_EXPERIMENTAL_DATA=ON `
  -DGR_BUILD_PYTHON_BUFFER=ON -DGR_BUILD_BENCHMARKS=OFF `
  -DGR_REQUIRE_PYTHON_TESTS=ON -DGR_TEST_TIMEOUT_MULTIPLIER=4 `
  "-DPython3_EXECUTABLE=$((Resolve-Path build/sdk-venv/Scripts/python.exe).Path)" `
  '-DCMAKE_C_FLAGS=/fsanitize=address /Zi' `
  '-DCMAKE_CXX_FLAGS=/fsanitize=address /Zi /EHsc' `
  '-DCMAKE_EXE_LINKER_FLAGS=/INCREMENTAL:NO /DEBUG' `
  '-DCMAKE_SHARED_LINKER_FLAGS=/INCREMENTAL:NO /DEBUG' `
  '-DCMAKE_MODULE_LINKER_FLAGS=/INCREMENTAL:NO /DEBUG'
& "$cmakeBin\cmake.exe" --build build-asan --config Release --parallel 4
$env:ASAN_OPTIONS = 'halt_on_error=1'
$env:PATH = "$msvcBin;" + $env:PATH
Copy-Item -LiteralPath "$msvcBin\clang_rt.asan_dynamic-x86_64.dll" `
  -Destination build-asan/Release/clang_rt.asan_dynamic-x86_64.dll
& "$cmakeBin\ctest.exe" --test-dir build-asan -C Release --output-on-failure
```

The DLL copy is build-local test support. `tools/test_installed_sdk.py` propagates
only an explicitly staged sanitizer runtime for a sanitizer-enabled Windows test
configuration into its relocated test prefix. It does not change Release install
contents or redistribute that runtime in the Python wheel.

Observed sequence, retained without overwriting evidence:

1. Initial instrumented run: 22/28 passed; six Python-dependent cases could not
   load the instrumented native DLL because Python's Windows DLL search did not
   locate the sanitizer runtime through PATH.
2. After staging the runtime: five of those six SDK cases passed. `python_binding`
   exceeded its original 120-second CTest watchdog. Its partial log shows the
   pinned historical record test had already passed. No sanitizer finding was
   reported.
3. The same complete 16-case `python_binding` suite passed in 474.26 seconds with
   the outer watchdog multiplied by 4 (480 seconds). Inputs, assertions, workload
   sizes and native cancellation/deadline settings were unchanged.

The final rerun command was:

```powershell
& "$cmakeBin\ctest.exe" --test-dir build-asan -C Release --output-on-failure `
  -R '^python_binding$'
```

Thus all 28 cases passed across the corrected runs; this is not a claim of one
single clean 28-case ASan invocation. Instrumentation covers the GR native
libraries, C ABI, CLI, optional CPython exporter and installed native consumers.
The Python interpreter itself is not instrumented. No ThreadSanitizer, leak,
power-loss or cross-platform validation claim is made.

Logs: `build-v0.4-asan.txt`, `ctest-v0.4-asan-initial{,-details}.txt`,
`ctest-v0.4-asan-sdk-timeout{,-details}.txt`, and
`ctest-v0.4-asan-python-final{,-details}.txt`.

Ruff checks passed; all 14 selected files were formatted. The historical example
passed its exact integer sum assertion (26), using the same native experiment
implementation as the C++ and C ABI consumers.

Benchmark invocations and exit status are recorded separately in
`capture-v0.4-commands.json`; each invocation has a `capture-v0.4-*.txt` log.
Performance captures run serially after all builds and tests completed.
The initial native timing variance prompted three additional alternating-order
matched pairs, recorded in `capture-v0.4-native-repeats-commands.json` without
replacing the first pair. Session drift also prompted three fresh frozen-v0.3
admission captures, recorded in `v0.3-pre-v0.4/admission-rerun-commands.json`.
Their original three baseline captures remain unchanged. Background activity,
power state and CPU frequency were not experimentally controlled.

`v0.4-source-artifacts.json` records source/build/vendor/SDK hashes and identifies
the tested native binaries, Python wheel, sanitizer binaries and CMake exports.
