# v0.7 SDK and package validation commands

Evidence date: 2026-10-17. This is engineering validation of an experimental
implementation, not adoption of a GR Standard or a claim of production readiness.

Final results: Release **40/40** CTests passed in **382.68 s**; the selected ASan
suite passed **39/39** in **832.22 s**. After the Python-only cleanup described
below, a freshly built and installed Release analysis wheel passed **9/9**
composition tests in **0.343 s**, plus the Python example. The ASan full run
already includes those nine tests (**6.323 s** inside package validation).
Both full configurations passed **57** analysis checks, **123** initial
visualization checks, and the diagonal suite's 32 oracle sizes and Function/error
contracts. The later large-fixture correction passed **127** visualization checks
in each configuration, as documented below.

## Full configurations

The machine-readable command arrays preserve exact absolute arguments:
[Release](commands-v0.7-release-final.json) and
[AddressSanitizer](commands-v0.7-asan-final.json). Their equivalent commands are:

```powershell
& $cmake -S . -B build -G 'Visual Studio 17 2022' -A x64 `
  -DGR_BUILD_TESTS=ON -DGR_BUILD_BINDINGS=ON -DGR_BUILD_BENCHMARKS=ON `
  -DGR_TEST_TIMEOUT_MULTIPLIER=1 "-DPython3_EXECUTABLE=$python"
& $cmake --build build --config Release --parallel 4
& $ctest --test-dir build -C Release -j 1 --output-on-failure

& $cmake -S . -B build-asan -G 'Visual Studio 17 2022' -A x64 `
  -DGR_BUILD_TESTS=ON -DGR_BUILD_BINDINGS=ON -DGR_BUILD_BENCHMARKS=OFF `
  -DGR_TEST_TIMEOUT_MULTIPLIER=8 "-DPython3_EXECUTABLE=$python" `
  '-DCMAKE_CXX_FLAGS=/fsanitize=address /Zi /EHsc' `
  '-DCMAKE_C_FLAGS=/fsanitize=address /Zi' `
  '-DCMAKE_EXE_LINKER_FLAGS=/INCREMENTAL:NO /DEBUG' `
  '-DCMAKE_SHARED_LINKER_FLAGS=/INCREMENTAL:NO /DEBUG' `
  '-DCMAKE_MODULE_LINKER_FLAGS=/INCREMENTAL:NO /DEBUG'
& $cmake --build build-asan --config Release --parallel 4
& $ctest --test-dir build-asan -C Release -j 1 --output-on-failure -E '^python_binding$'
```

The sanitizer configuration instruments project C/C++ targets, including vendored
SQLite C, the SDK bindings and independently built native package consumers. The
installed toolchain ASan runtime is staged only inside the build/test directories
before instrumented executables or DLLs load. Python and NumPy themselves are not
rebuilt with ASan. This is not ThreadSanitizer, cross-platform floating conformance,
power-loss testing, or an RSS bound.

Only the unchanged legacy `python_binding` suite is excluded from the ASan run,
consistent with the previously recorded sanitizer scope: its large record-capacity
fixture is particularly expensive under instrumentation. All 16 of its tests
remain covered by the full Release run. The newer data, runtime, buffer, module,
installed SDK and independent package suites remain in the sanitizer selection.

## Installed and independently built packages

The CTest packaging commands call `tools/test_installed_sdk.py`,
`tools/test_independent_package.py`, and `tools/test_module_packages.py` with the
current `--build`, `--source`, CMake executable and `--config Release`. The latter
two record each subprocess argument array, return code, stdout and stderr.

The module harness copies each package outside the central source directory,
builds against relocated installed CMake exports, installs and relocates the
packages, and builds a consumer that sees only installed dependencies. Python
consumers import installed wheels under isolated mode (`-I -B`). Native examples,
native conformance, shared-library Function composition, runtime submission,
portable Python composition, malformed input, resource limits and lifetime tests
are all exercised. Benchmark executables are built but not timed by these tests.

Versioned copies of package command records and artifact hashes are under
[`v0.7-packages/release`](v0.7-packages/release/prefixes.json) and
[`v0.7-packages/asan`](v0.7-packages/asan/prefixes.json). Each records all 51 copied
package source files and checks byte equality with the final workspace. Consumer
source equality is recorded separately. The ordinary installed SDK harness
streams to CTest rather than creating `commands.json`; its complete CTest section
and product hashes are preserved in the same directories.

Missing-SDK probes restrict package search to an empty root. Wrong-version probes
request incompatible exact declarations from the actual installed configurations;
they are not represented as rebuilding an older SDK. A separate genuine v0.6 SDK
rejection probe is preserved in
[older-sdk-v0.7-rejection.json](older-sdk-v0.7-rejection.json). No ignored v0.5 SDK
directory is required by the ordinary package tests.

## Corrections and retained evidence

The initial standalone package attempts are retained rather than overwritten:

- `modules-v0.7-release-initial.txt`: long Windows compiler-probe paths failed
  before package code ran. The harness now uses short unique directory names.
- `modules-v0.7-release-second.txt`: an empty Relation inventory in a native test
  fixture violated the existing kernel contract. The fixture was corrected to an
  Entity with an explicit empty participant inventory.
- `modules-v0.7-release-third.txt`: all package native checks passed, but CMake
  line-wrapping defeated a literal wrong-version diagnostic predicate. The
  predicate now normalizes whitespace while still requiring the actual
  exact-version rejection. Its continued consumer run is retained separately.

The early PowerShell Tee transcripts are UTF-16LE. The final build/test logs,
command JSON, package archives and this document are UTF-8.

After the full Release suite, the manifest dependency declaration was added to
each package's `CMAKE_CONFIGURE_DEPENDS`. Accepted copies were synchronized and
reconfigured. Touching each copied manifest then building `ZERO_CHECK` proved
automatic regeneration; native binaries were unchanged. See
[manifest-regeneration-v0.7-release-final.json](manifest-regeneration-v0.7-release-final.json).

One final Python-only cleanup makes `Analysis.import_value` explicitly close an
exported payload even when rejecting a non-byte carrier. Its regression retains
the original TypeError traceback while asserting the exported native buffer
handles are already closed and the original value remains usable. A targeted
Release analysis wheel rebuild/install and all nine installed composition tests
plus the Python example cover this change. The original Release artifact record
is retained as `artifacts-before-python-cleanup.json`; the final artifact record
points to the newly tested wheel and install directory. The final sanitizer
package copy includes the cleanup from the outset. No native package recompilation
was needed for this Python-only correction.

Performance captures follow validation in a separate serial measurement window.
Test execution times are not performance claims.

## Large visualization fixture correction

The first visualization benchmark attempt correctly rejected its 1,024-owner
fixture: 1,029 staged updates exceeded the MemoryStore transaction limit. The
production implementation was unchanged. The fixture now derives its publication
capacity from the store's 1,000-record limit and reserves one slot for the tracked
history manifest, allowing 999 user records per batch. Small fixtures retain their
original transaction identifiers and two publications; the largest fixture uses
three publications. Benchmark rows explicitly record these counts and limits.

Only the fixture header, benchmark source, conformance test and README changed.
The three visualization executables were rebuilt against each accepted installed
SDK/package configuration. The expanded test actually constructs and projects
1,024 owners, checking 3,073 occurrences, 1,029 selected records and three
publications. Targeted CTest passed **1/1**, with **127 checks**, in **4.58 s** for
Release and **180.52 s** for ASan. Both examples ran afterward. Their four scene
JSON/SVG files are byte-identical to the earlier small-example artifacts.

Exact commands/output are in
[visualization-fixture-v0.7-supplement.txt](visualization-fixture-v0.7-supplement.txt)
and each configuration's `visualization-fixture-commands.json`. Corresponding
artifact records prove that all production DLL hashes and the visualization
static-library hashes remained unchanged. The prior source files, benchmark
executable, source-equality record, artifact record and conformance record were
preserved before updating accepted copies. Final source equality remains 51/51
package files plus four consumer sources in each configuration. The complete
40/39 suites were not rerun for this fixture-only correction; these targeted
results supplement them. The failed benchmark capture remains distinct from the
subsequent corrected measurement window.
